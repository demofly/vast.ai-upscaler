# vast_upscale.py — AI-апскейл видео с людьми на GPU vast.ai

Один файл на Python (только стандартная библиотека), который от начала до конца автоматизирует апскейл видео до 1080p (или другого разрешения) на арендованном GPU в облаке **vast.ai** с помощью **SeedVR2** — лучшего на сентябрь 2026 открытого видео-апскейлера для реальной съёмки с лицами и телами (ByteDance, ICLR 2026, лицензия Apache-2.0).

## Что делает

| Этап | Что происходит | Прогресс/ETA |
|---|---|---|
| 1. Зависимости | Проверяет `python3 ≥ 3.10`, `ffmpeg/ffprobe`, `ssh`, `ssh-keygen`, `scp`, `rsync`; предлагает `sudo apt-get install …` (Ubuntu 24.04) | список ✔/✖ |
| 2. Сопряжение с vast.ai и Docker Hub | Показывает пошаговую инструкцию (аккаунт, пополнение от $5, создание API-ключа на `cloud.vast.ai/manage-keys`), запрашивает ключ, сохраняет в `~/.config/vastai/vast_api_key`; находит/генерирует SSH-ключ и регистрирует его в аккаунте; показывает баланс. Затем — доступ к Docker Hub для предсобранного образа: если учётных данных нет (аргументы/`DOCKER_USER`/`DOCKER_PASS`/сохранённый `~/.config/vastai/dockerhub.json`), печатает инструкцию (аккаунт, access-token с правами Read & Write, имя репозитория), запрашивает логин, токен (ввод скрыт) и репозиторий, проверяет доступ push через реестр, сохраняет. Пустой логин = работать без предсобранного образа. Затем — **рабочая папка скрипта** (кэш сборки образа и служебные файлы запусков `runs/`: сконвертированные видео, состояние, логи — чтобы ничего не росло рядом с исходниками и, под WSL2, внутри `ext4.vhdx`): при первом запуске спрашивается путь (показываются варианты с объёмом свободного места; под WSL2 — отдельно диск C:, на котором растёт `ext4.vhdx`, и смонтированные диски Windows `/mnt/d`…), выбор сохраняется в `~/.config/vastai/vast_upscale_settings.json`. Сменить путь: `--cache-dir <путь>` (синоним `--work-root`) — скрипт спросит, что делать со старыми данными: перенести в новый путь (по умолчанию), удалить или оставить; без терминала — `--cache-migrate move|delete|keep` (по умолчанию keep) | — |
| 3. Подготовка видео | Принимает файлы и/или папки (`--recursive`), анализирует через `ffprobe`, конвертирует в H.264 yuv420p с постоянным fps и чётными сторонами (SeedVR2 читает кадры через OpenCV — VFR/10-бит/HEVC ломают счёт кадров); пропускает уже готовые и уже ≥ целевого разрешения | бар по кадрам |
| 4. Подбор конфигурации | Ищет on-demand и interruptible-офферы, для каждого оценивает полное время run (pull образа + установка + веса + загрузка + обработка + скачивание) и стоимость всего run (аренда × оплачиваемое время + диск + трафик); по умолчанию берёт самый дешёвый run целиком (`--optimize cost`; есть `ratio` = $ × время, `balanced`, `speed`). Выбор автоматический и без ожидания: при управлении пулом — лучший по DLPerf/$; меню (Enter/номер, `iN` — подробности, `m` — ещё, `f` — фильтры и критерий, `r` — обновить, `q` — выход) и подтверждение заказа — только с `--interactive` | таблица ~время run / ~$ за run |
| 5. Развёртывание | **Набор пула без ожидания:** заказывает лучший оффер (бид = `min_bid × (1+--bid-margin)` для interruptible) и, пока ни одна машина не готова, каждые `--pool-scan` (15 с) перезапрашивает листинг: оффер лучше лучшего из заказанных в `--pool-improve` раз заказывается тоже (до 1+`--max-workers` одновременно); первая машина, прошедшая установку, становится основной, остальные входят в пул воркерами; не поднявшиеся за `--boot-deadline` (10 мин) удаляются. Каждый инстанс: ждёт `running` и рабочий SSH (прямой порт, иначе прокси), при сбое/таймауте удаляется, берётся следующий оффер; ставит SeedVR2 CLI (закреплённый коммит), зависимости, скачивает веса с HF с докачкой и проверкой sha256. Статус подъёма машины показывается одной строкой с временем последнего сообщения от неё (`12:34:56 H1 H200: loading pulling image`); одинаковый статус повторно не печатается (в терминале строка обновляется на месте, в логе `--daemon` — только при изменении) | бар установки по шагам и байтам весов |
| 6. Обработка | **Очередь чанков на этой машине.** Каждый файл режется на равные чанки (блоки) не длиннее `--block-seconds` (8) секунд видео (+8 кадров контекста спереди — см. раздел ниже); все чанки образуют одну очередь, из которой машины пула берут по одному: на инстансе заранее подгружено не больше чанков, чем у него видеокарт (обычно 1) — закончился текущий, в обработку идёт подгруженный, а следующий подгружается из очереди (лишний трафик при досрочном отключении не оплачивается). Каждый чанк — ровно на одной машине; готовый чанк **сразу** скачивается, видео собирается здесь, как только скачаны все его чанки; готовые чанки кэшируются между запусками (`<кэш>/chunks/`) и удаляются после сборки файла. Прогресс очереди — одной строкой с общим эстимейтом по фактической скорости пула. `rsync` каждого чанка (докачка при обрыве), `runner.py` в контейнере под `nohup` (переживает обрывы SSH, ждёт новых заданий), разбор строк прогресса SeedVR2 (`Encoding/Upscaling/Decoding batch i/N`, `Chunk i/N`), автоповтор при OOM с более щадящими настройками (tiled VAE → меньший batch → blockswap), фоновая докачка готовых чанков (`rsync --partial --inplace`, sha256), пока жив контейнер | бар очереди: кадры всех чанков, `чанки N/M · в работе · подгружено · ждут`, состояние каждой машины, ETA по скорости пула |
| 7. Сборка | Обычно уже сделана по ходу этапа 6: чанки склеиваются без перекодирования (`concat -c copy`, проверка числа кадров), подмешивается звук из исходника (AAC 192k), `<имя>_1080p.mp4` кладётся рядом с исходником, чанки этого видео удаляются из кэша; здесь дособираются последние | — |
| 8. Очистка | Останавливает и удаляет инстанс после скачивания всех результатов; при Ctrl+C/ошибке спрашивает (по умолчанию удаляет через 45 с) | итог: файлы, время, стоимость |

Прерванный запуск продолжается командой `--resume` (состояние в папке запуска — по умолчанию `<рабочая папка скрипта>/runs/<имя>-<hash>/state.json`, иначе `--workdir`; запуски старых версий со состоянием в `<папка входа>/.vast_upscale` подхватываются): готовые файлы не пересчитываются, загруженные не перезаливаются, установка не повторяется.

## Быстрый старт

```bash
python3 vast_upscale.py --check                     # шаги 1–2
python3 vast_upscale.py clip.mp4                    # результат clip_1080p.mp4 рядом
python3 vast_upscale.py ./videos --recursive --yes  # папка, без вопросов
python3 vast_upscale.py clip.mp4 --dry-run          # план и цены без заказа
python3 vast_upscale.py clip.mp4 --target 1440 --model 7b --optimize speed
python3 vast_upscale.py --list-instances            # что сейчас арендовано
python3 vast_upscale.py --destroy-instance 123456   # удалить вручную
python3 vast_upscale.py ./videos --daemon           # в фон; затем --attach / --status / --stop
DOCKER_USER=me DOCKER_PASS=token python3 vast_upscale.py ./videos --image-repo me/vast-upscale   # с предсобранным образом
```

## Ключевые параметры

* `--target 1080` — целевая **короткая** сторона (вертикальные ролики → 1080×1920). `--max-long-side` ограничивает длинную.
* `--model auto|3b|7b|7b-sharp` — auto: 7B fp16 при VRAM ≥ 40 ГБ (лучше на лицах), иначе 3B fp16; на 24–32 ГБ 7B идёт в fp8 + blockswap (медленнее).
* `--optimize cost|ratio|balanced|speed` — `cost` (по умолчанию): минимальная стоимость всего run; `ratio`: стоимость × длительность; `balanced`: стоимость + `--time-value` $/ч × длительность; `speed`: только время. Критерий и фильтры можно поменять прямо в меню выбора офферов (`f`).
* `--rental auto|on-demand|bid`, `--bid-margin 0.25`, `--max-price` — interruptible дешевле на 50–80 %, но инстанс могут перебить по цене; скрипт тогда каждые 5 с поднимает бид (к `min_bid` машины с запасом, иначе +3 %) — в пуле не выше цены соседнего взятого оффера, иначе до `--max-price`/+5 % — и ждёт возврата до `--resume-timeout` (30 мин); если это была единственная готовая машина пула, следующий оффер по DLPerf/$ берётся немедленно (см. «Пул машин»).
* Фильтры хостов: `--gpu "RTX 4090,RTX 5090,H100 SXM"`, `--min-vram 24`, `--min-reliability 0.95`, `--min-inet 200` (Мбит/с), `--min-cuda 12.6`, `--country DE,NL`.
* `--pre-downscale 540` — для сильно испорченных источников (модель тогда восстанавливает, а не «дорисовывает» поры).
* `--batch-size`, `--extra-args "…"`, `--seed` — тонкая настройка SeedVR2 CLI.
* `--block-seconds 8`, `--block-frames auto|N|0`, `--block-ctx 8` — чанки (см. раздел).
* `--keep-instance`, `--instance ID`, `--resume`, `--workdir` — папка этого запуска (по умолчанию `<рабочая папка скрипта>/runs/<имя>-<hash>`); `--cache-dir`/`--work-root` — рабочая папка скрипта (спрашивается при первом запуске, хранится в настройках), `--cache-migrate move|delete|keep` — что делать со старыми данными при смене
* Образ и канал: `--prebuild local|strict|inline|never|auto`, `--docker-user`, `--docker-pass`, `--image-repo`, `--snapshot-wait`, `--min-link 100`.
* Пул: `--pool-size 1` — регулятор числа активных машин (в терминале меняется клавишами `+`/`-`, `s` — состояние), `--pool-scan 15`, `--pool-improve 1.3`, `--pool-min 1`, `--boot-deadline 600`, `--max-workers 3`, `--min-worker-minutes 10`, `--no-parallel`; `--interactive` — меню выбора оффера и подтверждение заказа.
* Фон: `--daemon`, `--attach`, `--status`, `--stop`. Очистка: `--clear-chunks` — кэш очереди и все чанки (`chunks/` + `runs/`: готовые чанки, нарезка, конвертированные копии, состояние запусков), `--clear-cache` — вся рабочая папка (плюс веса, зависимости, слои образа); `--no-reuse-instances` — не подхватывать свои инстансы прошлых запусков.

## Блочная обработка: один файл — на несколько инстансов

Длинный ролик на одной карте — это часы (10 минут 24 fps ≈ 8,8 ч на RTX 4090 с 3B), а обрыв interruptible-инстанса стоил всей работы. Поэтому каждый файл режется на **чанки (блоки) не длиннее `--block-seconds` (8) секунд видео**: файл длиннее 8 с делится на равные чанки (≤ 8 с каждый, при 25 fps ≤ 200 кадров); `--block-frames N` — явно (но не длиннее того же предела), `0` — без чанков. Раскладка зависит только от файла и настроек, поэтому одинакова от запуска к запуску. Перед каждым блоком (кроме первого) добавляются `--block-ctx` (8) кадров **контекста** из исходника: они обрабатываются, но в результат не идут — ровно так SeedVR2 сам работает в потоковом режиме `--chunk_size` (контекст из сырых кадров предыдущего куска, выход контекста отбрасывается), поэтому стыки блоков не отличаются от стыков чанков в одиночном прогоне. Нарезка — кадрово-точный `-ss` по CFR-копии с перекодированием в H.264 CRF 10 (проверено покадрово), блоки называются `<имя>.bNNN.cfr.mp4`.

Каждый чанк — отдельное задание runner-а и, значит, единица всего остального: загрузки, очереди, work stealing и переноса на воркеры, докачки и кэша. **Готовый чанк скачивается немедленно** (фоновая докачка стартует по маркеру `.done`, не дожидаясь остальных), и как только скачаны все чанки видео, оно **сразу собирается на этой машине** (в отдельном потоке, пока GPU занят следующими файлами). **Кэш чанков:** скачанный чанк кладётся в `<рабочая папка>/chunks/<имя>-<hash требований>/<чанк>.mp4` с маркером `.json` (размер, sha256, кадры); «требования» — исходник (путь, размер, mtime), цель, `--max-long-side`, модель, seed, `--extra-args`, коммит SeedVR2, раскладка чанков. Следующий запуск с тем же исходником и требованиями (даже без `--resume`, после падения или Ctrl+C) берёт готовые чанки из кэша и пересчитывает только недостающие; если готово всё — GPU не заказывается, только сборка. Нарезка входа (`runs/<…>/<имя>.bNNN.cfr.mp4`) и CFR-копии живут в рабочей папке до полного завершения всей очереди и переживают перезапуск (следующий запуск не режет заново); удаляются, когда обработано всё. После сборки полного выходного файла все чанки этого видео удаляются из кэша (`meta.json` там описывает, чьи они). Перезапуск CLI на каждый чанк стоит 20–60 с загрузки модели — это плата за то, что потеря машины стоит не больше 8 с видео. На инстансе CLI пишет блок как PNG-последовательность (`--output_format png`), runner отбрасывает контекстные кадры и кодирует остальное тем же кодером и с теми же параметрами, что и сам CLI (`libx264 -pix_fmt yuv420p -preset medium -crf 12`), так что все блоки имеют идентичные параметры и склеиваются локально без перекодирования (`ffmpeg -f concat -c copy`, число кадров сверяется), после чего подмешивается звук. Накладные расходы: контекст (8/200 = 4 %), перезапуск CLI на чанк (загрузка модели; веса после первого раза в page cache контейнера), PNG-буфер чанка на диске инстанса (~1 ГБ, учтён в `--disk`). Потеря инстанса стоит не больше одного чанка (≤ 8 с видео).

## Что стоит знать

* Оценки скорости GPU (сек/кадр) — из опубликованных замеров; фактическая скорость измеряется после первого файла и уточняет ETA. Ориентир для 720p→1080p, 3B: RTX 4090 ≈ 2 с/кадр, RTX 5090 ≈ 1.5, H100 ≈ 0.6.
* Стоимость типичного 10-минутного ролика 720p→1080p: $0.3–2 в зависимости от GPU; плюс ~5–8 минут на запуск контейнера и загрузку весов (7.3 ГБ для 3B, 17 ГБ для 7B).
* Образ по умолчанию `pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime` (torch 2.8 — проверенная связка для SeedVR2 v2.5.24; поддерживает RTX 50xx/Blackwell).
* Отдельный проход восстановления лиц (CodeFormer/GFPGAN) намеренно **не** добавлен: на видео он даёт мерцание и «пластиковую» кожу, а SeedVR2 и так склонен к избыточной детализации; если нужно мягче — `--extra-args "--latent_noise_scale 0.1"`.
* **WSL2.** Фоновый режим (`--daemon`) живёт, пока открыто хотя бы одно окно WSL: при закрытии последнего окна Windows останавливает всю VM вместе с задачей — оставьте окно открытым и возвращайтесь через `--attach`. Виртуальный диск `ext4.vhdx` растёт по мере записи (веса модели, зависимости); если диск Windows под ним заполняется, VM останавливается мгновенно и без сообщений — скрипт проверяет место заранее, а всё уже скачанное и загруженное переиспользуется при следующем запуске. Место, освобождённое внутри VM, Windows не возвращается само (`ext4.vhdx` только растёт): в PowerShell от администратора `wsl --shutdown`, путь к диску — `(Get-ItemProperty HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss\*).BasePath` плюс `\ext4.vhdx`, затем либо `Optimize-VHD -Path "<путь>\ext4.vhdx" -Mode Full` (модуль Hyper-V, Windows Pro), либо `diskpart` построчно: `select vdisk file="<путь>\ext4.vhdx"`, `attach vdisk readonly`, `compact vdisk`, `detach vdisk`, `exit`; проще всего один раз включить `wsl --manage <дистрибутив> --set-sparse true` (WSL 2.0+), после чего место возвращается автоматически. Память VM по умолчанию ограничена половиной RAM Windows; чтение больших файлов (веса модели) наполняет page cache VM, и Windows эту память обратно не получает — скрипт сбрасывает прочитанное из кэша каждые 256 МБ (`posix_fadvise`), а в `%UserProfile%\.wslconfig` стоит задать `[wsl2] memory=…` и `[experimental] autoMemoryReclaim=gradual`, `sparseVhd=true` (WSL 2.0+), после чего `wsl --shutdown`. Файлы на дисках Windows (`/mnt/x`) читаются через 9p: скрипт читает их блоками по 4 МБ; прогресс слоя весов идёт по ходу чтения файла, а не по файлам.

## Почему SeedVR2

Исследование (сентябрь 2026): SeedVR2 остаётся консенсусным «лучшим open-weights видео-апскейлером для реальной съёмки» (fal.ai, ai-upscaler-benchmark, videoproc, обсуждения numz). FlashVSR v1.1 быстрее, но рассчитан на ×4 и «искажает дальние лица»; STAR/DOVE/Upscale-A-Video/VEnhancer — тяжелее и хуже по метрикам; новые статьи 2026 (DUO-VSR, InfVSR, CreativeVR, OSDEnhancer) либо без весов, либо требуют 80 ГБ; LTX-2.5-апскейлеры меняют идентичность лиц. Real-ESRGAN+GFPGAN — дешёвый, но покадровый (мерцание, «мыло» на коже).

## Новое в 1.2–1.3

**Предсобранный образ с вшитыми весами — собирается на вашей машине без Docker.** Режим `--prebuild local` (по умолчанию при наличии доступа к Docker Hub) не требует ни Docker-демона, ни podman — только `pip`, поэтому работает и в WSL2. На этапе 4, до таблицы офферов и покупки: определяется целевая модель (явная `--model` или по лучшему офферу при `auto`), тег ищется в реестре (`HEAD /v2/<repo>/manifests/<tag>`, работает и для приватных репозиториев); если образа нет, скрипт (1) читает манифест и конфиг базового образа `pytorch/pytorch:2.8.0-cuda12.8-cudnn9-runtime` из Docker Hub и монтирует его слои в ваш репозиторий через cross-repo mount (ничего не скачивая); (2) собирает слой софта: исходники SeedVR2 на закреплённом коммите (tarball с GitHub, без git), зависимости под Python контейнера через `pip install --target --platform manylinux… --python-version 3.11 --only-binary=:all:` (все теги manylinux до glibc базового образа; torch/torchvision остаются из базового образа и передаются как constraints, `opencv-python` заменяется на headless; пакеты, у которых на PyPI нет wheel — например `antlr4-python3-runtime` у omegaconf, — собираются локально в `wheelhouse` и подхватываются через `--find-links`, при новом таком конфликте wheel собирается автоматически и разрешение повторяется), статические `ffmpeg/ffprobe`, `/opt/vu/env.sh` с `PATH`/`PYTHONPATH`; (3) скачивает веса модели с докачкой и проверкой sha256 в кэш и собирает слой весов прямо из кэша (без копий и hardlink, gzip уровня 0 — safetensors не сжимаются); (4) публикует конфиг (с `PYTHONPATH=/opt/vu/pylib`, `PATH=/opt/vu/bin:…`) и манифест. **Слои не пишутся на диск:** tar.gz генерируется на чистом Python в отдельном потоке и через очередь кусков по 4 МБ уходит прямо в сокет **одним PATCH-запросом с `Transfer-Encoding: chunked`** — так же, как делает `docker push`: ни пауз между кусками, ни ожидания подтверждения каждого куска сервером (прогресс — по отправленным байтам), так что пик занятого места — это сами веса (≈ 7.3 ГБ для 3B, ≈ 17 ГБ для 7B) плюс ~2 ГБ зависимостей, а памяти процессу нужно около трёх кусков (~300 МБ). **Всё промежуточное кэшируется в `~/.cache/vast_upscale` (или `--cache-dir`) на случай пересборки:** исходники, wheel-и, разложенные зависимости (`pylib-py3.11/.done`), ffmpeg, веса (`models/*.safetensors` + маркер `.sha256ok`; докачка `.part` по Range), digest/diff_id готовых слоёв с отпечатком входа (`layers/*.json` — при совпадении отпечатка и наличии blob в реестре слой не собирается и не грузится; слой весов один на модель и переиспользуется для любого тега), а также **сессии загрузки** (`layers/upload-*.json`: Location, принятый объём, sha256 каждого 4-МБ куска) — после обрыва сети скрипт спрашивает у реестра, сколько принято, регенерирует слой детерминированно, сверяет принятую часть по хешам и продолжает PATCH с этого места; то же после падения скрипта или остановки всей VM. Ход сборки пишется в `<кэш>/build.log` (шаг, свободное место, RSS, сессии загрузки); неожиданные ошибки скрипта — с полным traceback в `<кэш>/crash.log`. Перед сборкой проверяется место: в файловой системе кэша и — под WSL2, если кэш внутри `ext4.vhdx`, — на диске Windows C:, где этот виртуальный диск растёт (когда диск Windows заполняется, Hyper-V останавливает VM целиком и сессия WSL обрывается без предупреждения). Если места мало, скрипт тут же предлагает выбрать другой путь кэша (например, `/mnt/d/vast_upscale_cache`) и переносит туда уже скачанное; `--ignore-disk-check` отключает остановку. Затем показывается таблица офферов и покупается рабочий инстанс из образа (с `image_login` для приватного репозитория; pull vast.ai не тарифицирует). **На инстансе из предсобранного образа ничего не скачивается и не устанавливается**: bootstrap только проверяет (веса нужной модели и их маркеры sha256, исходники SeedVR2, ffmpeg, импорт зависимостей) и запускает обработку; каждая проверка пишет в лог, что именно не так. Если чего-то нет, доустанавливается **только это** (исходники на месте — clone пропускается, зависимости импортируются — pip пропускается, веса с маркером — не скачиваются; веса на месте, но без маркера проверки — sha256 пересчитывается на инстансе, ничего не скачивается); но если в образе нет весов нужной модели или они не сходятся по sha256, это не тот образ — скачивать 7–17 ГБ на арендованной машине скрипт отказывается (`FAIL prebuilt-verify`), инстанс удаляется, а пул набирается только из офферов, которым по VRAM положена модель образа. То же при `--instance`/`--resume` на инстансе из вашего репозитория: bootstrap там только проверяет. В `pylib` записана версия Python, под которую собраны зависимости; если в контейнере другой Python (`env.sh` сравнивает), `pylib` убирается из `PYTHONPATH`, зависимости доустанавливает pip (несколько минут, без весов), а скрипт подсказывает пересобрать образ с `--base-python <версия>`. Версия Python входит в тег образа (`…-py311`); она определяется по метаданным базового образа, иначе принимается 3.11 (`--base-python`); если на образе нет rsync, передача файлов идёт через ssh-канал с докачкой (`tail -c +N | cat >>`). Через ваш аплинк уходят только новые слои: ~7.5 ГБ (3B) или ~17.5 ГБ (7B) один раз на модель. Тег образа: `seedvr2-<модель>-<коммит>-<hash базового образа>-py<версия>`; соответствия кэшируются в `~/.config/vastai/vast_upscale_images.json`. При смене тега (другая версия Python, новая схема тегов) слой весов **не грузится заново**: если digest-кэша нет, скрипт находит его в уже опубликованных образах репозитория по записи `weights <модель>` в history (Hub API `tags` → манифест → конфиг) и ссылается на тот же blob; если при этом весов нет и в локальном кэше — они и на вашу машину не скачиваются. Альтернативы: `--prebuild strict` — сборка снапшотом (`take_snapshot`) на самом дешёвом арендуемом инстансе; `inline`; `never`.

**Проверка полосы.** Сразу после SSH каждый инстанс (рабочий, сборщик, воркер) измеряет реальную скорость: загрузка/отдача через `speed.cloudflare.com` (резерв — CDN Hugging Face) и канал от вас по ssh. Ниже `--min-link` (100 Мбит/с) — инстанс удаляется, берётся следующий оффер.

**Пул машин по DLPerf/$.** Пока идёт обработка, каждые `--pool-scan` (15) секунд запрашивается листинг офферов (под те же фильтры и требования, что и при выборе); каждой машине пула и каждому офферу считается DLPerf/$ (индекс `dlperf` vast.ai на доллар в час; для interruptible — по нашему биду; без `dlperf` — TFLOPS/$). Лучший оффер берётся в пул (до `--max-workers` воркеров, не более одного заказа одновременно), если он лучше худшей машины пула не менее чем в `--pool-improve` (1.3) раз или в пуле меньше `--pool-min` (1) готовых машин и при этом есть неначатые блоки, а перенос их на новичка сокращает общее время с учётом его запуска (`--min-worker-minutes`). Худшая машина пула помечается на выбывание, когда есть *готовая* машина лучше её в `--pool-improve` раз: новых блоков она не получает, её неначатые блоки переезжают на лучшую, и как только она заканчивает текущий блок — удаляется; но выбывание не происходит, если после него в пуле останется меньше `--pool-min` машин, готовых принять блок прямо сейчас (SSH есть, runner запущен, не выбывает). Свободная машина забирает блоки у худших (work stealing); основной инстанс тоже может выбыть — тогда он удаляется, не дожидаясь воркеров. **Набор первичного пула** идёт по тем же правилам и без ожидания пользователя: лучший оффер заказывается сразу, пока он поднимается, листинг перезапрашивается каждые `--pool-scan` с, и оффер лучше лучшего из заказанных в `--pool-improve` раз заказывается тоже; первая машина, прошедшая установку, становится основной (её инстанс переходит основной сессии), остальные доустанавливаются и входят в пул воркерами (и сразу забирают блоки у худших либо, если работы нет, удаляются); инстанс, не прошедший установку за `--boot-deadline` (10 мин), удаляется — и при наборе, и позже. Не поднявшийся оффер заменяется следующим по списку. Старые ключи `--bargain-scan`, `--bargain-factor`, `--expensive-factor` остались синонимами.

**Регулятор числа машин.** `--pool-size N` (по умолчанию 1) — сколько активных машин (готовых + разворачивающихся) держать в пуле параллельно, не больше 1+`--max-workers` (по умолчанию 32 — потолок, чтобы клавиша `+` не упёрлась): при наборе первичного пула сразу заказываются N лучших офферов; пока активных меньше, на каждом скане берётся следующий лучший оффер по DLPerf/$ (без проверки выгоды; заказов одновременно — столько, сколько не хватает), новичку уходит половина хвоста очереди худшей машины; если активных больше требуемого — худшие по DLPerf/$ выбывают (доделывают текущий чанк и удаляются), но не ниже `--pool-min`. В терминале (не в `--daemon`) регулятор интерактивный: клавиши `+`/`-` меняют требуемое число на ходу, `r` — внеплановая проверка листинга офферов с вердиктом (взять ли лучший оффер и почему нет), `s` печатает состояние пула и очереди, `?` — подсказку. Текущее состояние всегда видно в строке прогресса: `пул: нужно N · активно A · разворачивается P` (и `ждут возврата K`, если кого-то перебили).

**Очередь, подгрузка и ребаланс.** Чанки не раздаются машинам заранее: очередь живёт на этой машине, каждая машина пула берёт из неё следующий чанк сама, держа подгруженными не больше `num_gpus` чанков; ребаланс происходит автоматически при любом подключении и отключении инстанса — новая машина сразу берёт из очереди, чанки отключившейся (текущий и подгруженные) возвращаются в голову очереди и перезапускаются на других, чанки в процессинге на остальных машинах не трогаются; если очередь пуста, а у кого-то есть подгруженный, но не начатый чанк и есть свободная машина — он возвращается в очередь. Инстанс, удалённый или остановленный **в обход скрипта** (руками в кабинете vast.ai), замечается на ближайшем скане по списку инстансов аккаунта: его чанки — в очередь, нагрузка перераспределяется на оставшийся пул, регулятор заказывает замену. Общий статус при этом не останавливается: ожидание возврата выбывшей машины идёт в фоне.

**Переиспользование инстансов после перезапуска.** При старте скрипт ищет в аккаунте работающие инстансы со своей меткой (`vast_upscale …`) и своим образом (базовым или любым тегом репозитория предсобранных), не занятые другими живыми фоновыми запусками, и включает их в пул без заказа (первый готовый — основной, остальные — воркеры), даже если рынок пуст; лишние по регулятору выбывают. Отключить: `--no-reuse-instances`.

**Перебили по цене.** Если interruptible-машину пула увели (или хост забрал GPU), её чанки (текущий и подгруженные) возвращаются в очередь и перезапускаются на других машинах; если она была **единственной готовой** в пуле, скрипт **немедленно** берёт следующий оффер по DLPerf/$ с рынка. Уведённой машине бид повышается **раз в 5 с** — к `min_bid` машины с запасом `--bid-margin`, иначе +3 % — но **не выше цены соседнего взятого оффера** (замены; если замена не заказывалась — ближайшей по DLPerf/$ машины пула). Как только машина возвращается, SSH переподключается, очередь на ней перезаписывается (что забрали — не повторяется), runner перезапускается, и она снова берёт чанки из очереди (лишнюю по регулятору выбывает худшая). Если она не вернулась за `--resume-timeout`, инстанс удаляется — чтобы поднятый бид не «выиграл» его позже впустую, — а run продолжается без неё, даже если это был основной инстанс: его поток остаётся координатором пула. Ожидание возврата идёт в фоне — общий статус, очередь и управление пулом не останавливаются.

**Требования к ресурсам как критерий отбора.** Перед поиском офферов по файлам считаются максимальные мегапиксели выхода и RAM на кадр; из них — минимальные VRAM (для 3B и 7B при batch 5: `base + 1 + 5·k·МП`), RAM (`6 ГБ + веса + штатный чанк ×1.2`) и диск (образ + веса + вход/выход ×1.3). Они печатаются строкой «Требования к инстансу: …», подставляются в запрос к vast.ai (`gpu_ram`, `cpu_ram`, `disk_space`) и проверяются для каждого оффера: если 7B не помещается под это разрешение при `--model auto`, оффер оценивается с 3B; если не помещается и 3B — скрывается. Та же модель памяти используется runner'ом в контейнере.

**Память.** Runner в контейнере подбирает batch по реально свободной VRAM (`nvidia-smi`) и мегапикселям выхода (консервативная модель ~1.5 ГБ/МП/кадр без тайлинга VAE и ~0.7–0.9 с тайлингом), включая тайлинг VAE, когда он даёт вдвое больший батч; чанк потокового режима — по лимиту RAM контейнера (cgroup v1/v2) с запасом ×2.5 на float32-копии. Локально печатается строка «память: VRAM … → batch …; RAM … → чанк …». OOM VRAM → лестница (tiled VAE → batch/2 → blockswap 16 → batch 5 + blockswap 32), убийство по RAM (SIGKILL) → чанк вдвое меньше.

**Фоновый режим.** `--daemon` отсоединяется от терминала (двойной fork), пишет `run.log` и `progress.json` в рабочую папку и регистрируется в `~/.config/vastai/vast_upscale_daemons.json`; `--attach` показывает хвост лога и живую строку прогресса (Ctrl+C отсоединяет, задача продолжается), `--status` перечисляет запуски, `--stop` шлёт SIGTERM — задача корректно завершается и удаляет все свои инстансы.

## Известные грабли (исправлены в 1.1)

* Запуск `bootstrap.sh` в фоне обязан быть в отдельной подоболочке с перенаправленными дескрипторами (`(setsid nohup … &)`), иначе ssh-команда ждёт конца установки и отваливается по таймауту — так было в 1.0 на реальном инстансе. Установка теперь идемпотентна (pid-файл), мёртвый процесс установки детектируется.
* ETA не «улетает» при паузах (скорость не опускается ниже 25 % средней).
* Батч 13 на 24 ГБ при выходе 1080p давал OOM — таблицы стали консервативнее, а решение принимается в контейнере по фактической VRAM.
